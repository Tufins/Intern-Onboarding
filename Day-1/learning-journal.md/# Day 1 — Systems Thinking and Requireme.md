# Day 1 — Systems Thinking and Requirements

## 1. What I Learned

- A system contains components that work together to achieve a goal.
- A system boundary separates what our team is building from external
  people, services, and systems.
- Functional requirements explain what a system must do.
- Non-functional requirements explain how well a system must perform.
- User stories describe a feature from a user's point of view.
- Acceptance criteria help us check whether a user story works correctly.
- A C4 Context diagram shows the system, its users, and external systems.
- An ambiguity log records unclear requirements and questions that need
  answers before development begins.

## 5. Feynman Check

### Explain functional vs non-functional requirements simply

Functional requirements describe what a system does. For example,
LearnLanka must allow a student to search for tutors.

Non-functional requirements describe how well the system performs.
For example, tutor search results must return in under 800 milliseconds
at the 95th percentile.

In simple words, functional requirements are the features, while
non-functional requirements describe measurable expectations for those
features and the system as a whole.
